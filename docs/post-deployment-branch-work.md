# 배포 이후 `feature/attendance-lottery-payout` 작업 정리

작성 기준: 2026-11-01 KST  
대상: 출석왕 프론트엔드 저장소와 인접한 `chesscode-server` 백엔드 저장소의 현재 워크트리

## 브랜치와 배포 상태

두 저장소 모두 현재 브랜치 이름은 `feature/attendance-lottery-payout`이다. 프론트엔드 HEAD는 `4706254`, 백엔드 HEAD는 `5965eee`이며, 각 저장소에서 확인한 HEAD는 `origin/main`과 같다. 이번 기능 변경은 커밋에 들어간 것이 아니라 대부분 워크트리에 미커밋 변경으로 남아 있다.

따라서 아래 내용은 이 브랜치에서 준비 중인 배포 이후 작업의 기록이다. **아래에 정리한 기능 변경이 운영에 배포됐다는 뜻은 아니다.** 백엔드 DB 마이그레이션도 운영 DB에 적용됐다고 확인하지 않았다.

## 1. 놀이터 탭을 포인트 탭으로 변경

- 하단 탭의 `놀이터` 문구와 플라스크 아이콘을 `포인트`와 P 코인 아이콘으로 변경했다.
- 포인트 탭 헤더, 복권 구매, 클로버 찾기 게임을 한 곳에 모았다.
- 알림 점의 접근성 문구도 `새 놀이터`에서 `새 포인트`로 바꿨다.
- 미션 설명과 새 소식 문구도 `포인트` 메뉴 명칭을 사용한다.
- 이전의 `개발 요구하기` 항목은 포인트 탭에서 빼고 `내 정보` 화면의 기타 영역으로 옮겼다.

주요 파일: `src/components/HomeTabBar.tsx`, `src/components/TabIcon.tsx`, `src/screens/LabScreen.tsx`, `src/screens/ProfileScreen.tsx`, `src/missions.ts`, `src/news.ts`.

## 2. 홈 화면 변경

### 연속 출석 배지

- 기존 선물 상자 아이콘과 `출석 n일째!` 표현을 없애고 홈 제목 옆에 `연속 출석 n일` 배지를 표시한다.
- 배지를 누르면 출석 도장 모으기 화면을 연다.
- 받을 수 있는 연속 출석 보상이 있으면 배지에 알림 점을 표시한다.
- 홈 진입 시 서버가 제공하는 기존 연속 출석일과 마지막 출석일을 로컬 연속 출석값의 최초 초기화에 사용한다.

### 출석복권 당첨자 배너

- 기존 홈의 출석점수 잔액/토스포인트 전환 블록을 제거했다.
- 해당 위치에 `최대 5,000원 당첨!` 배너와 `출석복권 받기` 진입 버튼을 배치했다.
- 서버에서 최근 실제 당첨자 목록을 받아 3초마다 한 명씩 회전한다. 클라이언트는 30초마다 목록을 다시 요청하고, 서버 응답은 서버 메모리에 5분간 캐시한다.
- 실제 닉네임은 마지막 두 글자만 남기고 앞부분을 `*`로 마스킹한다. 예: `홍*동` 형식이 아니라 닉네임 길이만큼 앞쪽을 별표로 가리고 끝 두 글자를 보여준다.
- 프론트엔드는 응답에서 최대 34명을 사용한다. 서버는 실제 당첨자 최대 30명과 더미 당첨자 4명을 금액순이 아니라 섞어서 반환한다.
- 더미 피드에서 1,000원은 현재 서버 코드의 고정 출력 목록에서 제외했다. 다만 더미 시드 SQL에는 1,000원 기록이 남아 있고, 출력 쿼리는 5·10·50·100원만 선택한다.

주요 파일: `src/screens/HomeScreen.tsx`, 프론트 API `/labs/attendance-lottery/recent-winners`, 백엔드 `AttendanceLotteryController`와 `AttendanceLotteryWinService`.

## 3. 포인트 탭 및 받은 토스포인트 표시

- 포인트 탭 오른쪽에 `출석왕에서 받은 토스포인트`와 누적 원화 금액을 표시한다. P 아이콘과 우측 화살표를 작은 크기로 배치했다.
- 해당 줄을 누르면 상세 모달을 띄운다. 상세 문구는 혜택 메뉴에서 받은 토스포인트를 확인할 수 있고, 모은 포인트를 현금처럼 사용할 수 있다는 안내다.
- 금액은 토스 계정의 현재 잔액이 아니라, 출석왕이 성공 지급했다고 기록한 누적 금액이다. 이미 사용한 포인트도 누적 합계에 포함된다고 안내한다.
- 포인트 탭을 열 때 대기 중인 클라이언트 지급 기록을 서버에 다시 보내고, `/points/toss-grants/total`의 누적 합계를 읽는다. 네트워크가 끊기면 마지막 로컬 표시값을 유지한다.
- 홈의 큰 출석점수 잔액 블록을 포인트 탭의 출석점수 블록으로 옮겼다. 이 블록에서 `출석복권 구매`를 연다.

주요 파일: `src/screens/LabScreen.tsx`, `src/components/TossPointsReceivedModal.tsx`, `src/utils/tossPromotion.ts`, 백엔드 `/api/attendance/points/toss-grants`.

## 4. 출석복권

### 화면과 구매 흐름

1. 포인트 탭에서 복권 구매 화면을 연다.
2. 복권 한 장 가격은 출석점수 10,000점이다. 구매 전 화면은 최대 당첨 5,000원과 `1P가 현금 1원 가치`라는 안내를 보여준다.
3. 사용자가 리워드 광고를 끝까지 보면 출석점수 10,000점을 로컬 잔액에서 차감한다.
4. 개발 모드에서는 로컬 확률 추첨을 한다. 운영 빌드에서는 서버의 `/labs/attendance-lottery/draws`가 당첨 금액을 정하고 `PENDING` 당첨 기록을 만든다.
5. 복권은 캔버스 긁기 UI로 표시한다. 약 48% 이상 긁으면 결과 공개 단계로 넘어간다.
6. 운영 빌드에서 긁기를 완료하면 Toss `Promotion.grantReward`로 토스포인트를 지급한다. 성공하면 지급 키를 사용해 서버 당첨 기록을 확정하고, 실패하면 복권을 `FAILED` 처리하고 로컬 출석점수를 돌려준다.

### 당첨 분포

서버 및 로컬 미리보기의 1,000,000 슬롯 기준 분포는 다음과 같다.

| 당첨액 | 확률 |
|---:|---:|
| 1원 | 25% |
| 2원 | 20% |
| 3원 | 43.9009% |
| 5원 | 10% |
| 10원 | 1% |
| 50원 | 0.08% |
| 100원 | 0.015% |
| 1,000원 | 0.004% |
| 5,000원 | 0.0001% |

1,000원 또는 5,000원이 당첨된 사용자는 30일 안에 다시 고액이 추첨되면 100원으로 바꾼다. 서버는 지급 완료된 고액 기록과 최근 5분 이내의 대기 기록을 확인한다. 로컬 미리보기에도 기기 로컬스토리지 기준 30일 제한을 둔다.

### 지급 기록

- `ATTENDANCE_LOTTERY_WINS`는 추첨 ID, 사용자, 당첨액, 프로모션 키, 상태(`PENDING`/`PAID`/`FAILED`), 추첨·지급 시각을 보관한다.
- `TOSS_POINT_GRANTS`는 사용자별 실제 토스포인트 지급 기록을 보관한다. 프로모션 키에 유니크 제약을 두어 같은 키의 중복 합산을 막는다.
- 사용자별 누적액 조회는 더미 지급을 제외하고 합산한다.
- 더미 계정은 별도 플래그로 식별하며, SQL 시드는 다섯 개 계정과 5·10·50·100·1,000원 기록을 넣도록 작성돼 있다. 홈 피드의 더미 출력은 현재 5·10·50·100원만 사용한다.

주요 프론트 파일: `src/components/AttendanceLotteryModal.tsx`, `src/utils/tossPromotion.ts`, `src/utils/tossRewardedAd.ts`.  
주요 백엔드 파일: `chesscode-server/service-attendance/src/main/java/com/schoolcheckin/attendance/lab/lottery/`, `.../points/`.  
DB 변경: `20261031_attendance_lottery_wins.sql`, `20261031_toss_point_grants.sql`, `20261101_dummy_attendance_lottery_data.sql`.

## 5. 클로버 찾기 게임 변경

- 기존에는 클로버를 모아 출석박스를 받은 뒤 상자를 열어 점수를 받았다. 이 UI와 박스 받기 단계를 클라이언트에서 제거했다.
- 네잎클로버를 제한 시간 1분 안에 찾으면 출석점수를 바로 적립하고 성공 화면에 금액을 보여준다.
- 일반 클로버 보상은 800~1,500점, 황금 클로버는 2,000~3,000점이다. 황금 여부는 서버가 새 게임 시작 시 5% 확률로 정한다. 현재 보상 금액 자체는 프론트에서 무작위로 계산한다.
- 한 번에 무료 3판을 제공하고, 모두 사용하면 리워드 광고를 보고 3판을 추가한다. 사용 횟수와 시도 ID 목록은 브라우저 로컬스토리지에 저장된다.
- 설명 화면은 유지한다. 보상 안내 그림은 선물상자 대신 클로버 아이콘을 쓰고, `출석점수를 바로 받아요` 및 짧은 성공 안내를 보여준다. 게임 상단 설명은 `설명` 버튼으로 연다.
- 성공 화면에서 점수 결과를 먼저 확인하고 다음 버튼을 누를 때 추가 플레이 안내를 열도록 바꿨다. 남은 횟수가 0이 되는 즉시 보상 화면을 덮어쓰던 자동 팝업은 제거했다.
- 클로버 성공 뒤 미션 진행도도 증가시킨다.

주요 파일: `src/screens/CloverFinderScreen.tsx`, `src/lab/clover/CloverGuideModal.tsx`, `src/lab/clover/CloverContinueModal.tsx`, `src/styles/lab.css`.

### 클로버 관련 잔존 백엔드

현재 프론트에서 박스 받기를 제거했지만 서버의 `CloverFinderService`는 기존 클로버 누적량·대기 박스 상태를 계속 갱신하며, 박스 claim API도 남아 있다. `LAB_CLOVER_BOX_CLAIMS` 기록 테이블과 `/labs/clover/boxes/recent-winners`도 추가됐으나, 새 클라이언트의 즉시 점수 지급 흐름은 이를 사용하지 않는다. 서버 및 데이터 모델에서 이전 박스 기능을 제거할지 별도 정리가 필요하다.

## 6. 출석 도장과 연속 출석 보상

### 연속 출석 일수 계산

- 출석 API가 성공한 뒤에만 `recordLocalAttendance()`를 호출한다.
- 한국 시간 날짜(KST)로 로컬스토리지에 현재 연속 일수와 마지막 출석일을 저장한다. 같은 날 여러 방에서 출석해도 하루만 증가하고, 하루를 건너뛰면 다음 출석 시 1일차부터 다시 시작한다.
- 서버의 기존 `appCurrentStreak`와 새 `appLastCheckInDate`를 로컬 값이 없을 때 한 번 가져오도록 했다. 이후에는 클라이언트 로컬스토리지가 연속 출석 카운터 역할을 한다.
- 홈 화면은 최초 서버 동기화 후 로컬 출석 이벤트와 브라우저 storage 이벤트를 구독해 숫자를 갱신한다.

### 도장 화면과 보상표

- 기존 선물상자 기반 보상 화면을 1~100일 도장 그리드로 바꿨다.
- 한 페이지에 8일(4열 × 2행)을 표시하고 좌우 스와이프로 넘긴다. 모달을 열면 현재 연속 출석 일수에 해당하는 페이지로 자동 이동한다.
- 보상은 1~7일차 별도 표를 쓰고, 8~100일차는 매일 보상한다. 10일 단위는 30,000점, 100일차는 100,000점이다.
- 기본 예정 보상은 1일 2,000점, 2일 5,000점, 3일 2,000점, 4일 5,000점, 5일 2,000점, 6일 5,000점, 7일 10,000점이다. 8~9일 및 10의 배수가 아닌 8~99일은 10,000점이다.
- 예정 보상 색은 10,000점 미만 브론즈, 10,000점 실버, 30,000점 골드, 100,000점 다이아 색이다. 출석 완료 상태는 보상 등급 색 대신 같은 완료 색을 쓴다.
- 출석한 도장은 현재 파란 계열로 표시한다. `받기`는 파란 칩으로 강조하며, 보상을 받은 카드는 파란 배경과 체크 표시가 있는 `받음`으로 구분한다. 출석왕 로고 도장 애니메이션을 수령 순간 보여준다.
- 화면 안내 문구는 `연속 출석이 쌓일수록 보상이 커져요! 놓치지 마세요.`로 정리했다.

주요 파일: `src/utils/localAttendanceStreak.ts`, `src/components/StreakRewardModal.tsx`, `src/hooks/useAttendancePoints.ts`, `src/screens/HomeScreen.tsx`, 백엔드 `/classrooms/my` 응답에 추가한 `appLastCheckInDate`.

### 도장 수령 동작의 현재 한계

현재 코드에서는 출석했다고 보상이 자동으로 `받음`이 되지 않는다. 도장 화면에서 보상 카드의 `받기`를 직접 눌러야 로컬 출석점수가 추가되고 `claimedDays`에 기록된다. 기존 요청의 자동 도장/자동 수령 동작과 다른 부분이며, 기기 변경·앱 재설치 시 연속 출석 및 수령 기록이 이어지지 않는다.

## 7. 출석점수와 다른 보상

- 내부 출석점수의 화면 표기를 `P`에서 `점`으로 정리했다. 토스포인트 표기는 `P`, 현금 가치는 원으로 구분한다.
- 신규 가입 환영점수를 1,000점에서 10,000점으로 바꿨다. `att-points-welcome-granted` 로컬 플래그로 중복을 막는다.
- 미션 5종 보상을 모두 10,000점으로 변경했다: 출석인사, 친구초대, 닉네임 변경, 클로버 3회 성공, 사진 인증방 2회 출석.
- 방 출석 선물은 방별 하루 1회 3,000~4,000점을 지급한다. 1~3등 보너스는 각각 2,000~2,500점, 1,500~2,000점, 1,000~1,500점이다.
- 방을 이동해도 보상 선물을 받을 수 있는 체크인은 하루 최대 3회로 제한한다. 이 상한도 현재 브라우저 로컬스토리지 기반이다.
- 문의/미션/출석 보상 모달의 단위 표기를 `P` 대신 `점`으로 바꿨다.
- 개발 모드에서는 앱을 다시 열거나 개발 미리보기에 진입할 때 `att-points-total`을 10,000점으로 설정해 복권 UI를 확인할 수 있게 했다. 운영 로직은 아니다.
- 로컬 출석점수 잔액은 `att-points-total` 로컬스토리지에 저장되고 클라이언트에서 더하고 뺀다. 현재 상한은 5,000,000점이다.

## 8. 토스포인트 지급 연결 및 데이터 의미

- `grantTossPromotionReward()`는 Toss 앱 여부와 SDK 지원 여부를 확인한 뒤 `Promotion.grantReward`를 호출한다.
- 성공 시 Toss가 반환한 promotion key, 지급액, 출처를 서버의 `POST /points/toss-grants`로 저장한다. 서버 장애 시 브라우저에 대기 목록을 두고 포인트 탭 진입 때 재시도한다.
- `GET /points/toss-grants/total`은 사용자별 실제 지급 합계를 반환하며 더미 지급을 뺀다.
- 복권과 포인트 전환은 기본적으로 동일한 Toss 프로모션 코드를 공유한다. 복권 코드는 `VITE_ATTENDANCE_LOTTERY_PROMOTION_CODE`로 바꿀 수 있고, 미설정이면 `POINTS_PROMOTION_CODE_REAL`을 사용한다.
- 예전 홈 화면의 `토스 포인트로 바꾸기` 진입 버튼은 제거했다. `ConvertPointsModal` 문구는 새 용어로 바뀌었지만 현재 화면에서 이 모달을 여는 연결은 없다. 현재 활성 흐름은 복권 당첨금을 Toss SDK로 지급하는 경로다.

### 지급 데이터 검증상 남은 문제

현재 클라이언트에서 Toss 지급을 실행하고 서버에는 성공 사실이라고 주장하는 요청을 보낸다. 서버가 Toss 영수증/서명을 확인하지 않고 요청의 금액·promotion key를 원장에 기록한다. 복권 추첨 API도 10,000 출석점수 차감이나 광고 시청 증명을 서버에서 확인하지 않는다. 서버 지급 내역과 복권 구매의 위변조 방지는 아직 완성되지 않았다.

복권 긁기 도중 모달을 닫으면 서버 추첨을 `FAILED`로 바꾸려고 하지만 로컬 10,000점 환불은 호출하지 않는 경로가 있다. 앱이 강제 종료된 경우에도 진행 중 추첨 복구가 보장되지 않는다.

## 9. 광고·진입 진단

- 리워드 광고 placement 타입에 `ATTENDANCE_LOTTERY` 등을 추가했다.
- 앱 진입 시 전체 초기 URL, 쿼리, 유저 에이전트 등을 보내던 진단 요청은 프론트에서 제거했다. 서버 진단 로그도 해당 값 자체 대신 포함 여부만 기록하도록 변경했다.
- 새 referrer 진단은 Toss 앱에서 `getSchemeUri()`의 `referrer`만 추출하고 앱 이름을 allowlist, referrer 문자열을 안전 문자 패턴으로 검증해 기록한다. 이 요청에는 로그인 토큰을 보내지 않는다.

주요 파일: `src/utils/reportAppEntryReferrer.ts`, `src/main.tsx`, `DiagnosticsController.java`.

- `public/rewards/lottery-box.png`, `public/rewards/lottery-box-blue.png` 자산을 추가했다. 현재 코드에서 이 파일명을 직접 참조하지는 않으며, 화면 복권 티켓은 CSS/SVG 구성이다.
- 연속 출석 도장 스탬프 애니메이션, 스와이프 페이지, 파란 수령 상태, 홈 당첨 배너 회전 애니메이션을 추가했다.

## 11. 서버·DB 변경과 배포 선행 작업

현재 백엔드는 `ddl-auto: validate` 설정이다. 엔티티가 참조하는 테이블/컬럼이 DB에 없으면 백엔드 기동 시 스키마 검증이 실패할 수 있다. 배포 전에 해당 운영 DB에서 마이그레이션 적용 여부를 확인해야 한다.

| 마이그레이션 | 목적 |
|---|---|
| `20261031_attendance_lottery_wins.sql` | 실제 복권 추첨·지급 상태 테이블과 유니크/조회 인덱스 생성 |
| `20261031_toss_point_grants.sql` | 토스포인트 지급 원장 테이블과 promotion key 유니크 제약 생성 |
| `20261101_dummy_attendance_lottery_data.sql` | 사용자·복권 지급 더미 플래그 추가, 더미 계정과 시연 지급 레코드 삽입 |
| `20261031_lab_clover_box_claims.sql` | 예전 클로버 출석박스 지급 이력 테이블 생성. 현재 UI에서는 사용하지 않지만 엔티티가 남아 있음 |

백엔드 파일 변경에는 출석 기록에서 마지막 앱 전체 출석 날짜를 읽어 `/classrooms/my` 응답에 `appLastCheckInDate`를 추가하는 부분, 미션 푸시 제목의 보상액 변경, 당첨 기록/원장 API, 클로버 박스 이력, referrer 진단 처리가 포함된다.

배포 순서 메모:

1. 운영 DB에서 기존 테이블·컬럼·시드 여부를 먼저 확인한다.
2. 새 테이블을 생성하고 더미 플래그/시드를 적용한다. 스크립트의 적용 여부와 부분 실행 여부를 먼저 확인한 뒤 중복 실행하지 않는다.
3. 필요한 테이블이 갖춰졌는지 확인하고 백엔드를 배포한다.
4. 백엔드 API가 정상인 것을 확인한 뒤 프론트엔드를 배포한다.
5. Toss 콘솔의 promotion/ad group 승인·한도·앱 표시 설정과 실제 Toss 앱 SDK 지급을 확인한다.

이 순서는 실제 배포가 진행됐다는 기록이 아니라 현재 코드의 의존 관계를 바탕으로 한 제안이다.

## 12. 카나리·무중단 전환 문서

## 13. 다른 작업으로 보이는 백엔드 워크트리 변경

현재 `chesscode-server` 워크트리에는 출석왕과 별개인 PocketQuest 변경도 함께 있다. `PQ_ROOM_MEMBERS`/`PQ_ROOMS` 소유자·활성 멤버십 변경 마이그레이션, `PQ_GOLD_ADJUSTMENTS` 도메인/저장소와 room ownership 통합 테스트가 미커밋·미추적 상태다. 이 문서는 출석왕 기능과 직접 관계가 없어 상세 동작을 합치지 않았으며, 출석왕 변경과 분리해 검토해야 한다.

## 14. 현재 확인된 미완료/주의 사항

1. 연속 출석일, 출석점수, 보상 수령 여부, 클로버 무료 판 수가 브라우저 로컬스토리지 기반이다. 재설치·기기 변경·저장값 초기화 시 이어지지 않고 클라이언트 변조도 가능하다.
2. 출석한 날의 보상 도장이 자동 `받음`으로 전환되지 않는다. 현재는 각 보상 카드에서 `받기`를 눌러야 점수와 수령 표시가 저장된다.
3. 클로버 점수 구간은 프론트가 정하고 점수도 프론트에서 난수로 생성한다. 서버는 성공 기록과 황금 여부를 관리하지만 새 점수 적립 원장을 갖고 있지 않다.
4. 클로버 백엔드는 이전 누적 클로버·출석박스 지급 코드를 아직 수행한다. 새 프론트는 해당 결과를 무시하므로 데이터와 제품 흐름이 어긋날 수 있다.
5. 복권 서버 추첨은 10,000점 잔액 차감과 광고 완료 사실을 확인하지 않는다. Toss 지급 원장 API도 Toss가 발급한 키의 진위를 서버에서 검증하지 않는다.
6. 긁기 화면을 닫을 때 복권 비용 환불이 누락되는 경로가 있다.
7. 복권 당첨 시연에는 서버 DB 더미 계정 및 지급 레코드가 사용된다. 현재 API는 더미 플래그를 함께 반환하지만 프론트 회전 배너는 이를 숨기지 않고 실제 이름 규칙처럼 마스킹해 보여준다.
8. `ConvertPointsModal`은 남아 있지만 현재 활성 화면에서 호출되지 않는다. 출석점수를 토스포인트로 직접 전환하는 기능이 필요한 경우 UI 연결과 서버/정책 흐름을 다시 정해야 한다.
9. 모든 DB 마이그레이션 및 프로모션 설정의 운영 반영 여부는 확인되지 않았다. 이 브랜치의 기능을 운영 기능으로 간주하면 안 된다.
